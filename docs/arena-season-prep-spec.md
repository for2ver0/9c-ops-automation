# 아레나 시즌 준비 프로세스 자동화 — 확정 스펙

## 1. 결론 요약

| 항목 | 내용 |
| --- | --- |
| **무엇을 결정했나** | 아레나 시즌 준비 업무를 **5개 스킬**로 자동화 |
| **핵심 원칙** | 서버가 이미 하는 일은 재구현하지 않고 **환산·프리뷰·대사·계산**에만 집중 |
| **핵심 제약** | 모든 단계의 **최종 확인·승인·실행은 사람** |
| **사람의 역할** | 상금 파라미터 입력, 검수, 백오피스 입력, 디스코드 전송, 지급 서명 |
| **현재 상태** | ⚠️ 이 행은 2026-08-30 최초 작성 시점(1순위만 착수) 기준의 스냅샷이다 — 이후 2~5순위도 모두 착수·구현됐다. 최신 진행 상황은 저장소 루트 `README.md` 참고. |
| **다음 단계** | (위와 같은 이유로 스냅샷) 최신 진행 상황은 `README.md` 참고 |

> 용어: **대사(對査)** = 산출·입력 값이 기준과 일치하는지 대조 검증. **불변식** = 항상 성립해야 하는 수치 관계(어기면 경고).
>
> 이 문서는 **의사결정과 준비 방향**을 담습니다. 세부 구현은 각 스킬 착수 시점에 별도로 정합니다.

## 2. 5개 스킬 한눈에 보기

> 역할 기술의 정본은 6-1입니다. 이 표는 요약이며, 내용이 어긋나면 6-1이 우선합니다.

| 순위 | 스킬 | 한 줄 역할 | 상태 |
| --- | --- | --- | --- |
| 1 | `arena-reward-table` | 상금 계산 + PNG + 불변식 검증 | **즉시 착수** |
| 2 | `arena-season-preview` | 블록 ↔ 날짜 프리뷰 + 입력 9개 대사 | 설계 차단 있음 |
| 3 | `arena-announce` | 공지 초안 + 티켓 수치 대사 | 값 차단만 |
| 4 | `arena-settlement-check` | 정산 결과 대사 (지급 실행은 사람) | 후순위, 합성 픽스처 필요 |
| 5 | `arena-season-checklist` | 1-4 상태 집계 + 시즌 캐시 점검 | 후순위, 파생 |

> 상태 열은 차단 **유형**만 표시합니다. 정확한 건수·차단 대상은 8-2가 정본입니다.

모든 스킬은 **네트워크(Odin·Heimdall·Thor)를 인자로** 받습니다. 상금 표·공지 스킬은 `SEASON`·`CHAMPIONSHIP`만 대상(오프시즌 공지 없음).

## 3. 준비 프로세스 전체 흐름

`상금 내용 작성` → `상금 표 생성` → `디스코드 공지` → `시즌 데이터 세팅` → `시즌 시작` → `시즌 종료` → `정산`

**범위 원칙.** 이 문서에서 "백오피스"는 두 도구를 가리킵니다 — 시즌을 저장·관리하는 **시즌 관리 백오피스**(ArenaService)와 상금·정산을 처리하는 **상금 계산 백오피스**. 백오피스가 **이미 자동으로 처리하는 일**(시즌 관리: 시즌 저장 시 종료 블록·라운드 전개·겹침 검사 / 상금 계산: 정산 시 랭킹·스테이킹·용기패스 자동 조회)은 스킬이 다시 만들지 않습니다. 이미 서버가 하는 계산을 재현하면 원본이 아니라 재현본을 검증하는 중복이 됩니다.

## 4. 사람 vs 스킬 역할

> 역할 기술의 정본은 6-1입니다. 이 표는 요약이며, 내용이 어긋나면 6-1이 우선합니다.

| 단계 | 사람 개입 지점 | 스킬이 하는 일 |
| --- | --- | --- |
| 1. 상금 내용 작성 | **입력만 사람** | 총 풀 · 그룹 배분 비율 · **보너스 배수 3종**을 담당자가 조절(기본값 자동). 계산은 스킬 |
| 2. 상금 표 생성 | **검수 후 반영** | 상금 표 계산 → PNG 렌더링 + 불변식 검증 |
| 3. 디스코드 공지 | **실행은 사람** | 공지 초안까지만. 티켓 수치를 라이브 정책 값과 대사 |
| 4. 시즌 데이터 세팅 | **검수 후 입력** | 블록 → 날짜 프리뷰와 입력값 대사. 새로 열 때만 날짜 → 블록 환산. 입력·저장은 사람 |
| 5·6. 시즌 시작/종료 | **실행은 사람** | 실행 자동화 = 낮음 / **점검 자동화 = 높음** |
| 7. 정산 | **검수 후 반영** | **대사 전용** (지급 리스트 준비는 백오피스가 이미 자동). 지급 실행은 사람 |

⚠️ **디스코드 전송은 자동화에서 제외.** 외부 공개 게시는 되돌릴 수 없고, discord.com은 이 환경의 방화벽 허용 목록에도 없습니다. 초안 생성까지로 한정.

**시즌 시작/종료를 "낮음"으로만 두지 않는 이유.** 시즌 캐시가 안 채워지면 `cached-block-info` API가 503(Service Unavailable) 오류를 내고, 블록 경계가 어긋나면 시즌이 통째로 틀어집니다. → **실행 자동화(낮음) / 점검 자동화(높음)** 로 분리.

## 5. 핵심 데이터 흐름

> **이 그림 하나로 스킬의 역할과 사람의 개입 지점을 전부 볼 수 있습니다.** 핵심은 `상금 명세`**와** `시즌 일정` **두 입력을 스킬이 가공하고, 실제 입력·전송·지급은 사람이 최종 수행한다**는 것입니다.

**입력 소스 두 개**

- **상금 파라미터** — 총 풀, 그룹별 배분 비율, **보너스 배수 3종**(스테이킹 lv2 = 0.5 / lv3 = 1.0 / **용기패스 — 시즌마다 다름, 아래 참고**). 상금 표 우측 6개 컬럼(조건별 1인 지급액)이 전부 이 배수에서 나옵니다.
    - ℹ️ 코드 `CreateDefault()`의 용기패스 `1.0`은 baseline이 아니라 **폼 프리필 초기값**입니다(운영자가 `ArenaRewardCalc.razor`에서 직접 입력). Heimdall CS9는 담당자 실측 스크린샷으로 **1.2**가 역산 확인됐지만(용기패스 조건 승수 2.2 = 1 + 1.2, `Courage Pass 13,750 = Basic 6,250 × 2.2`), Odin S39는 같은 방식으로 확인된 적이 없고, percentages/couragePassMultiplier가 시즌·타입마다 다르다는 것 자체가 Heimdall 실측으로 드러났다(`golden-fixture-answer-1.md`). ⚠️ **"1.2"를 다른 시즌에도 재사용 가능한 상수로 취급하지 말 것** — 백오피스에 표시되는 값 자체가 최신이 아닐 수 있고, 지난 시즌 실데이터를 대사해 보면 배수가 다르게 나온 사례도 보고됐다(2026-09-02). 매 시즌 담당자에게 그 시즌의 실제 값을 확인받아야 한다.
    - ⚠️ **여기서 말하는 "총 풀"은 코드상 `RankingPool` 입니다.** UI에 `Total Pool` / `Competition %` / `Ranking Pool` 세 칸이 있지만 계산에 쓰이는 건 `RankingPool` 하나뿐이고(`groupReward = RankingPool × pct / 100`), 나머지 둘은 `GenerateTierGroups`에서 사용되지 않습니다. **조절 입력은 `RankingPool`에 붙여야 합니다**(`TotalPool`에 붙이면 값을 바꿔도 표가 안 변함).
- **시즌 일정** — 시작 날짜/블록, 시즌 타입, 라운드 간격, 라운드 수. 담당자가 정함.

```
  [ 상금 명세 ]                          [ 시즌 일정 ]

  출력: 그룹별/조건별 지급액 · total_prize  티켓 정책 ID 2종
```

### 5-1. 시즌 데이터 세팅의 실제 동작

담당자가 `ManageSeasons.razor` "Add New Season" 화면에 값 **9개**를 넣는 작업입니다: `Season Group ID` · `Season Start Block` · `Round Interval` · `Total Number of Rounds` · `Arena Type` · `Required Medal Count` · `Total Prize` · `Battle Policy ID` · `Refresh Policy ID`

**시즌 관리 백오피스가 자동으로 처리하는 것** — 스킬이 다시 하면 중복입니다.

| 서버가 자동으로 | 내용 |
| --- | --- |
| 시작 블록 프리필 | 페이지 로드 시 `GetLastSeasonEndBlockAsync() + 1`로 미리 채움(담당자가 수정 가능) |
| 종료 블록 | `end = start + interval × count - 1` (입력칸 없음) |
| 라운드 전체 | N개 자동 생성. RoundIndex 1..N, 경계 연속 |
| 겹침 검사 | `IsBlockRangeOverlappingAsync` → 기존 시즌과 겹치면 예외로 거부 |
| `prize_detail_url` | UI 입력 항목 자체가 없음. 모델 기본값 고정 |

**서버가 안 해주는 것 = 스킬의 진짜 몫:**

1. **블록 → 날짜 프리뷰 (기본 모드)** — 프리필된 시작 블록과 라운드 수를 받아 "시작 M/D HH:MM / 종료 M/D HH:MM / 총 N일 / 라운드 N개"로 되돌려 보여주기. 담당자가 실제로 정하는 건 대개 **라운드 수(며칠짜리인지)**.
2. **날짜 → 블록 환산 (보조 모드)** — 시즌 사이에 공백을 두거나 새로 열 때만 필요.
3. **정책 ID 정합성 대사** — 숫자 직접 입력이라 오타 나면 챔피언십에 오프시즌 정책이 붙음. 서버는 검사 안 함.
4. **빈틈(gap) 검사** — 서버는 겹침만 막고 연속성은 안 봄.
5. **`Total Prize` ↔ 상금 표 총 풀 대사** — 두 곳에 따로 들어가는 숫자. ⚠️ **코드상 연결이 없는 운영 관례라 두 값이 다른 것 자체는 정상일 수 있음. 치명으로 두면 매번 오탐으로 스킬 산출물을 중단시키므로 경고(WARN) 등급** (8-2 참고).

## 6. 스킬 상세 · 판정 기준 · 수용 기준

**핵심 원칙.** 스킬은 서버가 안 하는 일에 집중하고, **상금 계산만 스킬이 직접 수행**(백오피스와 동일 로직). 계산이 갈릴 위험은 아래로 막습니다:

1. **기본값은 현재 운영 기준으로 고정** — 담당자가 명시적으로 조절할 때만 변경(`RankingPool`·비율·배수 3종). 단 `RankingPool` 기본값의 축은 8-2에서 결정.
2. **산출 시 불변식 검증** — 인원 합 500명 / 배분 비율 합 100%. **둘 다 서버가 검증하지 않으므로 스킬이 직접 검사합니다.** 특히 랭크 인원이 합을 넘으면 서버는 하위 랭커를 오류 없이 **조용히 건너뛰어** 정산에서 누락되고 나중에 CS로 드러납니다(근거는 7-1).
3. **산출 후 사람이 최종 확인** (핵심 제약)

**실지급은 등호가 아니라 상한입니다.** 조건별 1인 지급액은 1인 기본액에 조건 배수를 곱해 나오고, 전원이 최고 조건(스테이킹 lv3 + 용기패스)일 때만 그룹 실지급이 그룹 상금과 같아집니다. 여기에 정수 절삭이 더해져 **그룹별 실지급 ≤ Group Reward, 전체 실지급 ≤ 총 풀**이 항상 성립합니다. 이 부등호는 경고가 아니라 정상이며, 등호로 두면 매 시즌 오탐이 납니다.

### 6-1. 스킬 목록과 우선순위

우선순위는 매월 반복되고 실수 위험이 큰 **상금 표를 1순위**로 둡니다. **공수**는 착수 순서 판단용 상대 규모입니다. **이 표가 스킬 역할 기술의 정본입니다**(2·4는 요약).

| 순위 | 스킬 | 역할 | 이유 | 공수 |
| --- | --- | --- | --- | --- |
| 1 | `arena-reward-table` | `RankingPool`·비율·**배수 3종** + 인원·조건 → **상금 표 계산 + PNG 렌더링** + 불변식 검증 | 매월 반복·오타 위험, 계산의 중심 | 중 (PNG 근사 재현이 대부분) |
| 2 | `arena-season-preview` | **블록 → 날짜 프리뷰**(기본) / **날짜 → 블록 환산**(보조) + 입력 9개 대사(정책 ID · gap · `Total Prize`) | 서버가 안 하는 손검증. 틀리면 시즌 통째로 어긋남 | 중 (+ 합성 픽스처 2건) |
| 3 | `arena-announce` | 공지 초안 + **티켓 수치를 라이브 정책과 대사** | 전송은 사람. 대사가 최대 가치 | 소 (문구 틀 확보 시) |
| 4 | `arena-settlement-check` | **대사 전용** — 총 지급액 ≤ 총 풀 + 위험 항목 검출 | 실지급 사고·CS 방지 | **대** (합성 픽스처 4종이 작업량의 절반) |
| 5 | `arena-season-checklist` | 1-4 등급 집계 + 시즌 캐시 **읽기 점검만** | 위가 나온 뒤 묶는 게 자연스러움 | 소 (파생) |

**정산 대사(4순위)가 반드시 잡아야 할 실제 위험:**

- **용기패스 프리미엄 유저 100명 초과 누락** — 프리미엄 유저 조회가 100명으로 제한되고 페이지네이션이 없어, 프리미엄 유저가 100명을 넘으면 **조용히 누락되고 그만큼 덜 지급**됩니다. 대사가 잡아야 할 1순위 항목.
- **매칭 실패 2종 구분** — 스테이킹은 **agent 주소(계정 지갑)**, 용기패스는 **avatar 주소(캐릭터)** 기준. 두 종류를 나눠서 실패 목록을 뽑아야 합니다.
- **총 지급액 ≤ 총 풀** — 등호가 아님(위 원칙 2와 동일 이유).
- **스킵된 랭크 수 리포트** — 서버가 조용히 스킵한 하위 랭커 수를 집계해 표면화.

지급 후 거래(tx) 성공 여부 확인은 읽기 동작이라 자동화해도 안전합니다.

### 6-2. 판정 기준 (5개 스킬 공통)

> **판정 원칙:** 정상 범위는 `OK`, 사람이 확인해야 하는 이상 징후는 `WARN`, 데이터 자체가 잘못되어 진행하면 안 되는 경우는 `FATAL`입니다. **불변식 위반은 원칙적으로 치명(중단)이지만, "실지급 ≤ 총 풀"처럼 정상 범위인 부등호는 OK**(경고 아님).

### 6-3. 공용 모듈 지정

**블록 ↔ 시간 환산은 1·2·3순위가 전부 필요**하므로(표의 추정 날짜 / 프리뷰 / 공지 블록 정보) **단일 공용 모듈로 분리**합니다. 세 곳에서 따로 구현하면 블록타임 기준이 갈려 값이 어긋납니다.

### 7-2. 상금 표 레이아웃 스펙 (샘플 2종)
