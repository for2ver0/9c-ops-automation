# 아레나 시즌 등록 + 정산 실행 자동화 — 설계 결정 기록

## 1. 결론 요약

| 항목 | 내용 |
| --- | --- |
| **무엇을 결정했나** | 시즌 등록(`ManageSeasons`)과 정산 실행(NCG 지급 서명·전송)을 에이전트가 수행하도록 범위를 넓힘 |
| **누가 요청했나** | 담당자 (2026-09-02) |
| **기존 원칙과의 관계** | `arena-season-prep-spec.md` §1 "모든 단계의 최종 확인·승인·실행은 사람"에 대한 **명시적 예외**. 이 문서가 그 예외의 조건을 정의한다 |
| **핵심 안전장치** | 에이전트는 개인키에 접근하지 않는다(서명 전용 서비스 경유) + 서명·전송 직전 사람 확인 필수 + 감사 로그·알림 필수 |
| **현재 상태** | 담당자 확인 완료 6개 항목(§2) — 구현 착수 전 §4의 미해결 항목(안전장치 구체 수치·차등 키 권한)이 남아 있음 |

> 이 문서는 `arena-season-prep-spec.md`를 대체하지 않는다. 시즌 등록·정산 단계(§4의 4행·7행)에
> 한해 "실행은 사람"을 "에이전트가 실행하되 서명·전송 직전 사람이 확인"으로 바꾸는 addendum이다.
> 나머지 단계(디스코드 공지 등)는 기존 원칙 그대로 유지된다.

## 2. 배경

기존 스펙(`arena-season-prep-spec.md` §4)은 시즌 등록·정산 실행을 전부 사람이 하도록 못박아뒀다 —
`ManageSeasons` 등록은 "검수 후 입력(사람)", 정산은 "대사 전용, 지급 실행은 사람"이었다. 담당자가
이 경계를 옮기고 싶어 해서(2026-09-02), 아래 순서로 확인했다:

1. 범위가 시즌 등록만인지 정산 실행(NCG 서명·전송)까지인지 → **정산 실행까지 포함**
2. 서명 키를 에이전트가 직접 들고 있을지, 별도 서명 서비스를 경유할지 → **후자** (KMS/HSM류
   서명 전용 서비스, 에이전트는 "서명해줘" 요청만 보내고 개인키 자체는 절대 만지지 않음)
3. 사람마다 다른 키·다른 권한을 줄지 → **지금은 아님, 추후 개발**. 당장은 단일 접근 모델
4. 서명·전송 전 사람 확인이 필요한지 → **필요함**. 에이전트가 트랜잭션을 준비까지는 하되,
   실제 서명·전송(되돌릴 수 없는 지점)은 사람이 승인해야 실행된다
5. 감사 로그·알림 필요한지 → **무조건 필요**
6. 안전장치(한도·화이트리스트 등)가 전제조건인지 → **당연히 전제조건**

3번과 4번을 같이 보면, "에이전트가 정산을 실행한다"는 것의 실제 의미는 **에이전트가 준비·제출까지
자동으로 하고, 서명·전송이라는 마지막 되돌릴 수 없는 동작 앞에서 사람이 승인 버튼을 누른다**는
뜻이다 — 완전 무인 자동 서명이 아니다. 이 점이 처음 요청("사람은 사후에 결과만 확인")보다 실제로는
더 보수적인 모델로 좁혀졌다는 걸 명시해둔다.

## 3. 확정된 아키텍처 원칙

- **에이전트는 개인키를 절대 보관·조회하지 않는다.** 서명은 별도 서명 서비스(KMS/HSM 등)가
  담당하고, 에이전트는 "이 트랜잭션을 서명해줘"라는 요청만 그 서비스에 보낸다. 키가 에이전트
  프로세스·메모리·로그 어디에도 노출되지 않아야 한다.
- **서명·전송(되돌릴 수 없는 지점) 직전에 사람의 명시적 확인이 있어야 한다.** 에이전트가 계산한
  값(등록 파라미터, 정산 대상·금액)을 사람이 실행 직전에 검토·승인하기 전에는 서명 요청 자체가
  나가지 않는다.
- **모든 서명·전송 행위는 감사 로그로 남고, 실행 즉시 담당자에게 알림이 간다.** 예외 없음.
- **한도·화이트리스트 등 안전장치는 이 기능이 존재하기 위한 전제조건이다.** 안전장치가 갖춰지지
  않은 상태로 이 기능을 부분적으로만 쓰는 것도 허용하지 않는다 — 전부 갖춰진 뒤에 켠다.
- 사람마다 차등된 키 접근 권한은 **이번 범위에 포함하지 않는다.** 지금은 단일 접근 모델로
  시작하고, 차등 권한은 별도 후속 설계로 다룬다.

## 4. 미해결 항목 — 착수 전 반드시 정해야 함

이 항목들은 "당연히 필요하다"는 원칙 합의는 됐지만, 구체적인 수치·메커니즘은 아직 정해지지
않았다. 코드를 쓰기 전에 아래가 채워져야 한다.

| 항목 | 필요한 결정 |
| --- | --- |
| 서명 서비스 선정 | 어떤 KMS/HSM(또는 그에 준하는 서비스)을 쓸지, 에이전트가 그 서비스를 호출할 인증 방식(별도 서비스 계정? 스코프는?) |
| 사람 확인 UX | 서명 직전 확인을 어디서 받나 — Slack/디스코드 승인 버튼? 별도 대시보드? 승인자는 누구로 제한되나? 타임아웃되면 어떻게 되나? |
| 한도 | 트랜잭션당 상한액, 일별/시즌별 누적 상한, 초과 시 자동 거부인지 추가 승인인지 |
| 화이트리스트 | 정산 수신 주소를 어떻게 사전에 검증·고정하나 (예: 랭킹/스테이킹 데이터에서 유도된 주소를 서명 직전 별도 소스로 재검증) |
| 이상 탐지 | 무엇을 "이상"으로 보나 — 예: 지급 총액이 RankingPool을 벗어남, 동일 주소로 중복 서명 요청, 평소 대비 비정상적 트랜잭션 수 |
| 감사 로그 저장소 | 어디에 남기나(레포 로컬 로그 파일? 외부 로깅 시스템?), 보존 기간, 접근 권한 |
| 알림 채널 | 실행 즉시 알림을 어디로 보내나(디스코드/Slack/이메일), 실패 시 알림도 포함되나 |
| 롤백 불가 전제 확인 | 서명·전송 후 오류 발견 시 대응 절차(트랜잭션 자체는 못 무르지만, 후속 정정 절차는 있어야 함) |
| 차등 키 권한 (후속) | §3에서 이번 범위 밖으로 뺐지만, 나중에 다룰 때 이 문서를 갱신할 것 |
