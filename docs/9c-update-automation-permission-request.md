# 정규 업데이트 자동화 — 권한 요청 (승인자에게 그대로 전달 가능)

설계 문서("나인 크로니클 업데이트 자동화 설계") §5에서 정리된 권한 3건입니다. 전부 **1차
블로커** — 이 중 하나라도 승인되면 그 조각에 해당하는 스킬 착수가 바로 가능합니다. 이미
구현된 [`release-guard`](../.claude/skills/release-guard/SKILL.md)의 절반(일관성·헤드 대조)은
이 3건 전부 승인 전에도 만들 수 있었던 부분이라 먼저 구현·커밋해뒀습니다. 나머지는 아래
권한이 있어야 착수 가능합니다.

각 항목은 **승인 여부만 확인되면 되는 것**과 **승인과 별개로 사람이 값을 채워야 하는 것**을
분리해뒀습니다 — 승인 자체는 셋 다 예/아니오로 답할 수 있는 수준으로 최소화했습니다.

---

## ① 밸런스 시트(Vault) 읽기 접근

**요청 내용**: 담당자가 관리하는 밸런스 데이터 시트(구글 시트)를, 기존에 쓰던 읽기 전용
서비스 계정(`readonly-sheet@...391004`)에 공유해주세요. **새 계정을 만들지 않습니다** —
이미 존재하는 계정에 시트만 추가로 공유하면 됩니다.

**왜 필요한가**: 설계 문서의 1차 필수 스킬 3종(`spec-to-datasheet`/`datasheet-validate`/
`datasheet-to-csv`) 전부가 이 시트를 읽어야 동작합니다. 지금은 셋 다 착수조차 못 하고
있습니다.

**승인되면 바로 풀리는 것**: 위 3개 스킬 착수.

**승인 범위**: 읽기 전용. 자동화가 시트에 직접 쓰지 않습니다 — 산출물은 정제 이슈로 나오고,
사람이 그걸 보고 시트에 값을 입력합니다(설계 문서 D1 원칙).

**별개로 필요한 확인 2건** — 이 항목의 승인과는 무관한, **서로 다른 자격증명 체계**라 따로
확인이 필요합니다(자세한 내용은 [자체 확인 문서](9c-update-automation-self-check.md)):
- 노션 페이지가 `spec-to-datasheet`이 쓸 integration에 Connections로 공유됐는지 —
  **Notion 접근 권한**을 가진 사람이 확인
- `Atralupus/lib9c`에 `GITHUB_FOCKED_REPO_WRITE_TOKEN`(오타가 그대로 굳어진 실제 키 이름 —
  `FORKED`로 "고치면" 안 됨)으로 push가 실제로 되는지 — 이 **GitHub 토큰**을 보유한 사람이
  확인

## ② S3 `Event.json` 읽기 + 백업 저장 위치 결정

**요청 내용**: S3 버킷 `9c-assets`의 `live-assets/Json/Event.json` 경로에 대한 **읽기 전용**
접근과, 아래 두 백업 저장 위치 중 하나를 골라주세요.

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| (a) 전용 git 저장소(개인) | 변경 이력만 커밋 → diff·타임스탬프·작성자 추적 쉬움 | fine-grained PAT은 개인 레포만 적용돼 토큰 재발급 잦고, 개인 계정 거버넌스 이슈 |
| (d) planetarium org 전용 신규 레포 | git 추적 이점은 (a)와 동일 + 개인 계정 거버넌스 이슈 없음, org PR 토큰 범위 활용 | 레포 신설·권한 부여를 org 관리자가 해야 함 |

설계 문서는 (a)와 (d)를 함께 검토하되 **결정은 이 요청 문서와 함께 내려달라**고 남겨뒀습니다
(둘 다 git 추적 이점이 있어 우열이 크지 않고, 조직 운영 방침에 달린 선택이라서입니다).

**왜 필요한가**: `Event.json`은 Backoffice `/event-banner-manager`가 S3에 PutObject로 즉시
덮어쓰는 방식이라(PR도 백업 로직도 없음) 변경 이력이 전혀 안 남습니다. `release-guard`가
주기적으로 스냅샷을 떠서 diff를 보존하는 게 이 항목의 목적입니다.

**승인되면 바로 풀리는 것**: `release-guard`의 나머지 절반(스냅샷/백업)을 이어서 구현.

**보존 기간 참고**: 변경 이력 자체는 git 특성상 영구 보존되지만, S3 원본 버킷은 읽기
전용이라 같은 곳에 못 쓰므로 최소 90일 이상 백업 보존을 권장합니다(설계 문서 부록 D-1).

## ③ 디스코드 게시 경로 확보

**요청 내용**: `announce-fanout`이 초안을 올릴 디스코드 채널/웹훅 경로를 확보해주세요.

**왜 필요한가**: 지금은 웹훅/봇 미보유라 이 스킬은 게시 단계 전까지(초안 생성)만 만들 수
있습니다. 다만 이건 다른 두 건과 달리 **1차 블로커가 아니라 게시 단계 착수 시점에만
필요**합니다 — `announce-fanout` 착수 시점까지는 급하지 않습니다.

**승인되면 바로 풀리는 것**: `announce-fanout`의 게시 단계(초안은 웹훅 없이도 만들 수 있음).

## 승인 안내

세 항목은 **서로 독립적**입니다 — 하나만 먼저 승인돼도 그 조각을 바로 이어서 만들 수
있습니다. 순서를 정해야 한다면 ①(밸런스 시트)이 1차 필수 스킬 3개를 한 번에 푸는 항목이라
우선순위가 가장 높습니다.
