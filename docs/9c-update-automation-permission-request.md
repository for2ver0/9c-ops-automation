# 정규 업데이트 자동화 — 권한 요청 (승인자에게 그대로 전달 가능)

설계 문서("나인 크로니클 업데이트 자동화 설계") §5에서 정리된 권한 요청입니다. 번호는
**설계 문서 원문 번호를 그대로 씁니다**(⑦⑧⑨ — 임의로 다시 매기지 않음, 대조 시 혼선 방지).
①⑤가 빠진 이유는 각 항목 안에 적어뒀다.

> 이 문서는 세 차례 교정됐다. 1차는 팀 피드백으로 "①만 승인되면 1차 필수 스킬 3개가 다
> 풀린다"는 과장된 claim, ⑦(밸런스 시트 소유·운영 절차) 질문 누락, ⑧(S3) 저장 위치를
> 승인자에게 떠넘긴 것, 키 보관·주입 방식 누락 4가지를 고쳤다. 2차는 **①(밸런스 시트 접근)
> 요청 자체가 필요 없다는 게 실제 확인으로 드러나** 통째로 뺐다. 3차는 **⑤(디스코드 게시
> 경로)도 같은 이유로 뺐다** — 담당 팀 확인 결과 애초에 자동 게시 경로 자체가 존재하지
> 않고, 항상 사람이 수동으로 올리는 구조로 운영되고 있었다.

## ① 밸런스 시트 읽기 접근 — 요청 철회 (이미 공개 상태로 확인됨)

`datasheet-validate`가 읽어야 할 실제 작업 시트
(`docs.google.com/spreadsheets/d/1Di903g3_mxdDd6gZuNhczE4MXwFI-lWnOqzuVPbGM7k/`)를 무인증
`GET`으로 직접 열어봤더니 **이미 "링크가 있는 사용자는 로그인 없이 접근 가능"(unlisted)
상태**였다. 문서 안 데이터 탭(`CollectionSheet`, `MaterialItemSheet`,
`EventDungeonStageSheet` 등 lib9c 스키마와 일치하는 실제 밸런스 수치가 담긴 탭들)을 6개
샘플로 CSV export해봤는데 전부 인증 없이 200으로 읽혔다. 그래서 **서비스 계정에 별도로
시트를 공유해달라고 요청할 필요가 없다** — `datasheet-validate`는 권한 승인 없이 바로
착수할 수 있다.

**다만 확인해서 알아두면 좋은 것 (요청 아님)**: 지금 공개 상태가 의도된 것인지, 앞으로도
유지될 것인지는 확인 안 됐다. 나중에 누군가 실수로 비공개로 바꾸면 `datasheet-validate`가
그 시점부터 조용히 막힐 수 있으니, **"이 시트, 계속 지금처럼 공개로 두실 건가요?"** 정도는
가볍게 확인받아두면 좋다 — 승인을 기다릴 일은 아니고, 대답이 늦어도 착수는 막지 않는다.

**⑦ 같이 여쭤봐도 좋을 것**: 밸런스 데이터를 CSV로 내보내는 기존 도구를 지금 누가
소유·운영하고 있나요? 게시 주기와 내보내기 절차도 궁금합니다. `datasheet-to-csv`를 "기존
도구 확장"으로 갈지 판단할 때 필요합니다 — 이것도 급한 승인 요청은 아닙니다.

**별개로 필요한 확인 2건** — 이건 시트와 무관한, 서로 다른 자격증명 체계라 따로 확인이
필요합니다(자세한 내용은 [자체 확인 문서](9c-update-automation-self-check.md)):
- ② 노션 페이지가 `spec-to-datasheet`이 쓸 integration에 Connections로 공유됐는지 —
  **Notion 접근 권한**을 가진 사람이 확인
- ⑨ `Atralupus/lib9c`에 `GITHUB_FOCKED_REPO_WRITE_TOKEN`(오타가 그대로 굳어진 실제 키 이름 —
  `FORKED`로 "고치면" 안 됨)으로 push가 실제로 되는지 — 이 **GitHub 토큰**을 보유한 사람이
  확인

## ⑤ 디스코드 게시 경로 — 요청 철회 (자동 게시 경로 자체가 없음, 확인됨)

담당 팀에 문의한 결과:

- **디스코드는 자동 게시 경로가 아예 없습니다.** 웹훅도 봇도 없고, 전부 사람이 직접
  올리는 수동 단계입니다.
- 채널은 **Planetarium 디스코드의 `announcement` 채널**로 확인됐습니다.
- 월간 릴리즈 공지는 파이프라인의 고정된 마지막 단계입니다(APV 범프 → `latest.json` →
  인게임 노트·팝업·깃북 → 디스코드) — 설계 문서 3장의 "배포(APV·latest.json)가 노트·공지보다
  선행한다"는 서술과 정확히 일치하고, `context/9c-release-flow.md`로도 재확인됐습니다.
- 아레나 시즌 공지는 이미 `arena-announce` 스킬이 영문 초안까지만 만들고, 전송은 담당자가
  검토·수정 후 직접 게시하는 걸로 운영 중입니다.

그래서 **웹훅/봇을 만들어달라고 요청할 필요가 없습니다** — 애초에 그런 걸 만드는 게 목표가
아니라, `announce-fanout`도 `arena-announce`와 같은 패턴(초안까지만 만들고 게시는 항상 사람)
으로 설계하면 됩니다. 필요한 건 권한이 아니라 **`announcement` 채널이라는 사실 하나**뿐이고,
그건 이미 확인됐습니다.

**승인 없이 바로 풀리는 것**: `announce-fanout` 착수 — 웹훅/봇 대기 없이 초안 생성 스킬로
바로 만들 수 있습니다.

## ⑧ S3 `Event.json` 읽기 + 백업

**요청 내용**: S3 버킷 `9c-assets`의 `live-assets/Json/Event.json` 경로에 대한 **읽기 전용**
접근을 부탁드립니다.

**저장 위치**: 저희 쪽에서 먼저 정했습니다 — **planetarium org 하위에 전용 신규 레포를
만드는 방식(설계 문서 부록 D-1의 (d))으로 진행하겠습니다.** 개인 계정에 라이브 감사 기록을
두는 거버넌스 이슈가 없고, org PR 토큰 범위를 그대로 쓸 수 있어서입니다. 이견 있으시면
말씀해주세요 — 개인 전용 git 레포 안(부록 D-1의 (a))도 검토해뒀습니다.

**보존 기간**: 전용 레포에 변경 이력만 커밋하는 방식이라 git 특성상 사실상 영구 보존됩니다.

**키 보관·주입 방식 — 이게 없으면 스냅샷 장치 자체가 성립하지 않습니다**: S3 자격증명은
1Password에만 보관하고, 스냅샷 스크립트를 실행할 때마다 사람이 직접 값을 주입하는 방식으로
시작합니다(설계 문서 D1 방침 — 1차는 전부 사람이 직접 실행). 자동 주기 실행(cron 등)으로
넘어가려면 이 키 관리 체계를 별도로 다시 설계해야 하는데, 그건 지금 요청 범위가 아닙니다.

**왜 필요한가**: `Event.json`은 Backoffice `/event-banner-manager`가 S3에 PutObject로 즉시
덮어쓰는 방식이라(PR도 백업 로직도 없음) 변경 이력이 전혀 안 남습니다. `release-guard`가
주기적으로 스냅샷을 떠서 diff를 보존하는 게 이 항목의 목적입니다.

**승인되면 바로 풀리는 것**: `release-guard`의 나머지 절반(스냅샷/백업)을 이어서 구현.

**참고**: 위 키 관리 체계가 확정되기 전까지는 백업 보장이 0인 구간이 생깁니다. 그동안은
설계 문서 방침대로 **위험한 작업(팝업/이벤트 변경) 직전·직후 수동 스냅샷 2회**로 잠정
대응합니다.

## 승인 안내

승인이 필요한 건 이제 ⑧(S3) 하나뿐입니다. ①과 ⑤는 둘 다 "권한이 없어서 못 한다"가 아니라
"애초에 그 권한이 필요 없었다"는 게 확인으로 드러나 빠졌습니다 — `datasheet-validate`와
`announce-fanout` 둘 다 승인 없이 바로 착수할 수 있습니다.
