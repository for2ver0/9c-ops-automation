# release-notes (부분 구현 — 구조만 잡는 초안 도구, 헤딩 레벨은 검증됨·2단 불릿 구조만 지원·GitBook 확장 문법은 미검증)

> 이 스킬은 2026-09-01 세션에서 처음 SKILL.md로 작성됐다. 설계 문서("나인 크로니클
> 업데이트 자동화 설계")가 이 스킬의 실행 조건으로 적어둔 "⑥ 깃북 작성 방식 확인 + GitHub
> 토큰(확보만)"이 조사 결과 절반은 틀린 전제였다는 게 드러났다 — 왜 그런지, 그리고 이
> 스킬이 왜 "구조만" 잡는 수준에 그치는지 먼저 읽을 것.

## 무엇이 왜 이렇게 됐는지

### GitHub 토큰이 애초에 필요 없었다

`docs/9c-update-automation-self-check.md` ⑥ 항목에서 확인한 내용이다. 깃북 공개
페이지(`docs.nine-chronicles.com/introduction/intro/release-notes`)의 HTML에는 GitBook
자체가 내장한 메타데이터가 있는데, 여기에 `"gitSync":{"direction":"export", ...
"repoName":"planetarium/nine-chronicles-docs"}`가 명시돼 있다. **`direction`이 "export"**라는
게 핵심이다 — 깃북이 GitHub 레포로 **내보내는(백업하는)** 방향이지, 레포에서 깃북으로
**가져오는** 방향이 아니다. 즉:

- 릴리즈 노트는 **깃북 에디터에서 직접 작성**된다(설계 문서가 "확인 안 됨"으로 남겨뒀던
  미확인 1의 답이 이걸로 나왔다 — "깃북에 직접 작성한다"는 추측이 맞았다).
- `nine-chronicles-docs`(비공개 레포)는 그 내용을 자동 백업하는 대상일 뿐, 편집 소스가
  아니다. GitHub PR로 반영하려는 접근은 다음 export 때 되돌려질 수 있다 — 시도하면 안 된다.
- 그래서 이 스킬은 GitHub에 전혀 접근하지 않는다. 산출물은 **사람이 깃북 에디터에 그대로
  붙여넣을 마크다운 텍스트**면 충분하다.

### 정확한 형식(마크다운 문법)은 2026-09-04에 상당 부분 확인됐다

`arena-announce`는 담당자가 실제 과거 디스코드 공지 3건을 통째로 받아서 바이트 단위로
재현되는 고정 템플릿을 만들었다(`arena-announce-template.ts` 모듈 doc). 이 스킬은 원본
마크다운 소스(`nine-chronicles-docs`, 비공개)를 그렇게 통째로 받은 적은 없지만, 렌더링된
HTML을 `release-guard`의 `parseGitbookHead`와 같은 방식(직접 grep, WebFetch AI 요약 아님)
으로 최근 릴리즈 5개(200430~200470)를 대조해 아래를 확인했다:

- **버전 헤딩** — `<h2 id="id-{APV}">{APV}</h2>`, `v` 접두사 없는 순수 숫자. `## {APV}`로
  쓴다. (기존에 이미 확인된 것.)
- **카테고리 헤딩도 `<h3>`로 확인됨(신규)** — `### {category}`로 쓰는 게 맞다.
- **다만 3단 구조도 실재하고, 이 스킬은 아직 지원 안 함(신규, 중요)** — 5개 중
  2개(200450·200430)는 `<h3>` 카테고리 밑에 `<h4>` 하위 카테고리가 또 있었다("New Stages",
  "Buff Limit Adjustments" 등). 지금 `--input` 형식(`{category, items}`)엔 이 3단째를 넣을
  자리가 없다 — 필요하면 카테고리 이름에 구분을 녹이거나 여러 섹션으로 쪼개서 우회해야
  한다.
- **카테고리는 고정 타입이 아님(신규, 중요)** — WebFetch로 먼저 받은 AI 요약은 "New Event
  Dungeon / Game Improvements / Bug Fixes / Content Balance Adjustments / NCU"를 "표준
  카테고리"라고 제시했는데, 원본 HTML을 직접 대조해보니 부정확했다. 5개 릴리즈 중
  3개(200430·200440·200460)가 그중 일부(각각 1~4개)를 실제로 썼지만, 15개 실제 제목 중
  겹친 건 6개뿐이고 나머지 2개 릴리즈(200450·200470)는 하나도 안 겹쳤다 — 대부분은
  "Adventure Boss Rework", "New Runes — PETPOP" 같은 그 회차 전용 기능명이었다. 즉 그
  5개는 "가끔 재사용되는 이름"이지 "표준 카테고리 목록"은 아니다. **그래서 고정 카테고리
  목록을 만들지 않는 기존 설계가 맞았다는 게 재확인됐다** — 카테고리 이름은 계속 매번
  사람이 정한다.
- **항목은 대개 `<li>` 완결 문장** — `- ${item}` 마크다운 불릿 가정과 일치(200470·200440 두
  섹션에서 확인). 다만 **5개 중 200450은 `<li>`가 0건**이고 전부 `<p>` 문단 + `<strong>`
  소제목으로만 쓰여 있었다 — 불릿이 상시 형식은 아니라는 뜻이라, 이 도구가 항상 찍는
  `- ${item}` 형태가 안 맞는 회차도 있을 수 있다(그때는 사람이 붙여넣기 전에 손봐야 한다).
  표(`<table>`)는 5개 릴리즈 전부에서 0건이라 상시 쓰는 문법이 아니다.
- **여전히 미확인**: 콜아웃/힌트 블록, 이미지 삽입 같은 GitBook 전용 확장 문법(이번 5개엔
  안 나왔을 뿐 안 쓰인다는 보장은 아님).

정리하면 "확인은 됐지만 이 스킬이 아직 표현 못 하는 것"(3단 구조, 불릿 아닌 문단형 회차)과
"여전히 확인 자체가 안 된 것"(GitBook 확장 문법)은 다르다 — 전자는 언젠가 `--input` 형식을
확장하면 풀리고, 후자는 원문 마크다운 소스가 있어야 풀린다. 초안 맨 아래엔 이제 "헤딩
레벨(##/###)은 검증됨, GitBook 전용 확장 문법만 미검증"이라는, 더 정확해진 경고를 붙인다
(예전엔 "마크다운 문법 전부 미검증"이라고 뭉뚱그렸었다) — 다만 이 경고문 자체는 앞의 두
표현 한계까지는 아직 언급하지 않는다. 그 둘은 §6 "다음에 할 일"에 각각 별도 항목으로
올려뒀다.

## 1. 무엇을 하는가

1. **버전 대사** — 지정한 APV가 지금 깃북 최신값보다 큰지(FATAL 아니면 이미 게시된 값
   재사용), `+10` 관행과 맞는지(WARN — 깃북 릴리즈 노트 헤딩 200330~200470(15개)이 예외
   없이 +10 간격이었다는 실측 관찰, 2026-09-01 확인. 관행일 뿐이라 FATAL로 막지 않는다).
2. **섹션 대사** — 섹션이 하나도 없으면 FATAL, 항목이 없는 섹션이나 이름이 중복된 섹션이
   있으면 WARN.
3. **초안 조립** — 버전 헤딩 + 카테고리별 섹션 + 항목 목록으로 정리한 마크다운 텍스트를
   만든다.

## 2. 실행

```bash
# --input 파일 형식 (JSON 배열)
# [{ "category": "신규 콘텐츠", "items": ["신규 스테이지 501-510 추가"] }, ...]

bun run "$(git rev-parse --show-toplevel)/tools/9c/release-notes.ts" --apv 200490 --input ./release-note-sections.json

# JSON으로
bun run "$(git rev-parse --show-toplevel)/tools/9c/release-notes.ts" --apv 200490 --input ./release-note-sections.json --json
```

FATAL(이미 게시된 버전 재사용, 섹션 없음)이 있으면 exit 1이고, 사람이 읽는 출력에서는
초안 자체를 보여주지 않는다(`arena-announce`와 동일 패턴 — "확인 후 재실행하세요"만
표시). `--json`은 FATAL이어도 항상 `draft`를 포함한다 — 자동화 파이프라인이 원인
분석용으로 쓸 수 있게.

## 3. 판정 기준 요약

| 검사 | OK | WARN | FATAL |
| --- | --- | --- | --- |
| APV가 이미 게시된 값보다 최신 | 큼 | — | 같거나 작음 |
| APV가 +10 관행을 따름 | 일치 | 불일치(의도한 건너뜀일 수 있음) | — |
| 섹션 존재 | 1개 이상 | — | 0개 |
| 빈 섹션 없음 | 전부 항목 있음 | 항목 0개인 섹션 존재 | — |
| 섹션 이름 중복 없음 | 중복 없음 | 중복 존재 | — |

## 4. 범위 밖 (의도적으로 뺀 것)

- **문구 창작** — 섹션 제목·변경 항목 텍스트를 이 도구가 짓지 않는다. 전부 입력값 그대로.
- **정확한 깃북 마크다운 문법 보장** — 헤딩 레벨(버전 `##`·카테고리 `###`)은 2026-09-04에
  실제 렌더링 HTML로 직접 확인했지만(§"정확한 형식" 참고), 나머지 문법(리스트, 굵게 등)은
  표준 마크다운을 가정할 뿐 GitBook 특유의 요구사항을 검증하지 않았다. `<h4>` 하위 카테고리
  (3단 구조)와 불릿 없이 문단으로만 쓰인 회차(200450)는 실재가 확인됐는데도 `--input` 형식이
  "카테고리 + 불릿 항목" 2단뿐이라 아직 표현할 수 없다.
- **실제 깃북 게시** — GitHub PR도, 깃북 API 호출도 하지 않는다. 사람이 초안을 검토하고
  직접 깃북 에디터에 붙여넣는다(D4 원칙).
- **시트 diff·PR 이력 자동 수집** — 설계 문서는 이 스킬의 입력을 "시트 diff + 기획서 + PR
  이력"으로 그렸지만, 이번 착수는 그 입력을 사람이 준비해서 `--input`으로 넘기는 것까지만
  가정한다. `datasheet-validate --baseline-csv`의 diff 출력을 사람이 요약해서 섹션으로
  옮기는 식으로 연계할 수는 있지만, 자동 연결은 만들지 않았다.

## 5. 근거

- `docs/9c-update-automation-self-check.md` ⑥ — 깃북 페이지에 내장된 `gitSync` 메타데이터
  (`direction: export`)로 GitHub 토큰이 불필요함을 확인한 조사 기록.
- `.claude/skills/release-guard/SKILL.md` / `tools/9c/lib/release-guard.ts`의
  `parseGitbookHead` — 버전 헤딩 렌더링 패턴(`<h2 id="id-{APV}">{APV}</h2>`)의 실측 근거,
  이 스킬이 그대로 재사용.
- 2026-09-01 깃북 릴리즈 노트 페이지 헤딩 직접 확인 — 200330~200470(15개)이 예외 없이
  +10 간격, 200480은 아직 없음(0건). 그중 200400~200470(8개)은 날짜도 확인됨(설계 문서
  부록 C, 2026-01-27~08-25) — +10 관행의 근거.
- 2026-09-04, 사용자가 준 릴리즈 노트 공개 페이지 URL을 `parseGitbookHead`와 같은 방식(원본
  HTML 직접 grep)으로 재조사 — 200430~200470(5개) 대조 결과 카테고리 헤딩이 `<h3>`임을
  확인. 같은 대조에서 5개 중 2개(200450·200430)에 `<h4>` 하위 카테고리가 있다는 것(3단
  구조 실재, 이 스킬 미지원)과, 200450은 `<li>`가 0건이고 `<p>`+`<strong>`로만 쓰였다는
  것도 함께 확인됐다. 먼저 시도한 WebFetch 요약이 "표준 카테고리 5종"이라고 제시한 것도
  원본 HTML로 재검증: 5개 릴리즈 중 3개(200430·200440·200460)가 그 이름 중 일부(각각
  1~4개, 5개 회차의 `<h3>` 카테고리 제목을 다 합친 15개 중 6개)를 실제로 썼지만 나머지
  2개(200450·200470)는 하나도 안 겹쳐, "표준 목록"이 아니라 "가끔 재사용되는 이름"이라는
  게 드러났다. 이 발견으로 "AI 요약은 마크다운 문법 근거로 못 믿는다"는 기존 판단이
  재확인됐고, 고정 카테고리 목록을 안 만드는 설계가
  맞다는 것도 재확인됐다.

## 공백 항목 판정 (2026-09-03 "조용한 OK" 점검으로 추가)

`빈 섹션 없음` 검사가 `items.length === 0`만 봐서, `items: ["", "  "]`처럼 **항목은 있는데
전부 공백**인 섹션이 통과했다. 그 상태로 전체 판정이 OK였고, 초안에는 빈 불릿이 그대로
찍혔다(실측):

```
### 버그 수정

- 
-   
```

지금은 공백만 있는 항목을 "없는 것"으로 세어, 전부 공백이면 빈 섹션으로(WARN), 일부만
공백이면 `빈 항목이 섞인 섹션`으로 따로 알린다.
