# release-notes (부분 구현 — 구조만 잡는 초안 도구, 문구·정확한 마크다운 문법은 검증 안 됨)

> 이 스킬은 2026-09-01 세션에서 처음 SKILL.md로 작성됐다. 설계 문서("나인 크로니클
> 업데이트 자동화 설계")가 이 스킬의 실행 조건으로 적어둔 "⑥ 깃북 작성 방식 확인 + GitHub
> 토큰(확보만)"이 조사 결과 절반은 틀린 전제였다는 게 드러났다 — 왜 그런지, 그리고 이
> 스킬이 왜 "구조만" 잡는 수준에 그치는지 먼저 읽을 것.

## 무엇이 왜 이렇게 됐는지

### GitHub 토큰이 애초에 필요 없었다

`docs/9c-update-automation-self-check.md` ⑥ 항목에서 확인한 내용이다. 깃북 공개
페이지(`docs.nine-chronicles.com/introduction/intro/release-notes`)의 HTML에는 GitBook
자체가 내장한 메타데이터가 있는데, 여기에 `"gitSync":{"direction":"export", ...
"repoName":"planetarium/nine-chronicles-docs"}`가 명시돼 있다. **`direction`이 "export"**라는
게 핵심이다 — 깃북이 GitHub 레포로 **내보내는(백업하는)** 방향이지, 레포에서 깃북으로
**가져오는** 방향이 아니다. 즉:

- 릴리즈 노트는 **깃북 에디터에서 직접 작성**된다(설계 문서가 "확인 안 됨"으로 남겨뒀던
  미확인 1의 답이 이걸로 나왔다 — "깃북에 직접 작성한다"는 추측이 맞았다).
- `nine-chronicles-docs`(비공개 레포)는 그 내용을 자동 백업하는 대상일 뿐, 편집 소스가
  아니다. GitHub PR로 반영하려는 접근은 다음 export 때 되돌려질 수 있다 — 시도하면 안 된다.
- 그래서 이 스킬은 GitHub에 전혀 접근하지 않는다. 산출물은 **사람이 깃북 에디터에 그대로
  붙여넣을 마크다운 텍스트**면 충분하다.

### 그런데 정확한 형식(마크다운 문법)까지는 검증 못 했다

`arena-announce`는 담당자가 실제 과거 디스코드 공지 3건을 통째로 받아서 바이트 단위로
재현되는 고정 템플릿을 만들었다(`arena-announce-template.ts` 모듈 doc). 이 스킬은 그런
원문 샘플이 없다 — 원본(`nine-chronicles-docs`)이 비공개라 이 세션이 직접 열어볼 수 없고,
렌더링된 HTML에서 실제 마크다운 소스(헤딩이 `#`인지 `##`인지, 리스트 문법 등)를 역산하는
것도 신뢰할 수 없다.

그래서 확실한 것만 쓴다:

- **버전 헤딩** — release-guard의 `parseGitbookHead`가 이미 실측 검증한 렌더링 패턴
  (`<h2 id="id-{APV}">{APV}</h2>`, `v` 접두사 없는 순수 숫자)을 그대로 반영해 `## {APV}`로
  쓴다. 이건 직접 관측(HTML grep)이라 신뢰도가 높다.
- **섹션 제목·항목 문구** — 전부 사람이 입력값으로 준 것을 그대로 옮긴다. 이 도구가 새로
  짓지 않는다. WebFetch로 실제 릴리즈 노트 몇 건의 섹션 구성("New Content", "Balance
  Changes" 등)을 훑어봤지만, AI 요약을 거친 정보라 정확한 마크다운 문법의 근거로 쓰기엔
  약하다고 판단해 고정 카테고리 목록도 만들지 않았다 — 카테고리 이름은 매번 사람이
  정한다.
- 초안 맨 아래에 "마크다운 문법 미검증, 과거 페이지와 비교해 형식을 맞추라"는 경고를
  항상 붙인다.

## 1. 무엇을 하는가

1. **버전 대사** — 지정한 APV가 지금 깃북 최신값보다 큰지(FATAL 아니면 이미 게시된 값
   재사용), `+10` 관행과 맞는지(WARN — 깃북 릴리즈 노트 헤딩 200330~200470(15개)이 예외
   없이 +10 간격이었다는 실측 관찰, 2026-09-01 확인. 관행일 뿐이라 FATAL로 막지 않는다).
2. **섹션 대사** — 섹션이 하나도 없으면 FATAL, 항목이 없는 섹션이나 이름이 중복된 섹션이
   있으면 WARN.
3. **초안 조립** — 버전 헤딩 + 카테고리별 섹션 + 항목 목록으로 정리한 마크다운 텍스트를
   만든다.

## 2. 실행

```bash
# --input 파일 형식 (JSON 배열)
# [{ "category": "신규 콘텐츠", "items": ["신규 스테이지 501-510 추가"] }, ...]

bun run "$(git rev-parse --show-toplevel)/tools/9c/release-notes.ts" --apv 200490 --input ./release-note-sections.json

# JSON으로
bun run "$(git rev-parse --show-toplevel)/tools/9c/release-notes.ts" --apv 200490 --input ./release-note-sections.json --json
```

FATAL(이미 게시된 버전 재사용, 섹션 없음)이 있으면 exit 1이고, 사람이 읽는 출력에서는
초안 자체를 보여주지 않는다(`arena-announce`와 동일 패턴 — "확인 후 재실행하세요"만
표시). `--json`은 FATAL이어도 항상 `draft`를 포함한다 — 자동화 파이프라인이 원인
분석용으로 쓸 수 있게.

## 3. 판정 기준 요약

| 검사 | OK | WARN | FATAL |
| --- | --- | --- | --- |
| APV가 이미 게시된 값보다 최신 | 큼 | — | 같거나 작음 |
| APV가 +10 관행을 따름 | 일치 | 불일치(의도한 건너뜀일 수 있음) | — |
| 섹션 존재 | 1개 이상 | — | 0개 |
| 빈 섹션 없음 | 전부 항목 있음 | 항목 0개인 섹션 존재 | — |
| 섹션 이름 중복 없음 | 중복 없음 | 중복 존재 | — |

## 4. 범위 밖 (의도적으로 뺀 것)

- **문구 창작** — 섹션 제목·변경 항목 텍스트를 이 도구가 짓지 않는다. 전부 입력값 그대로.
- **정확한 깃북 마크다운 문법 보장** — 헤딩 레벨(`##`)은 렌더링 관측 기반 최선의 추정이고,
  나머지 문법(리스트, 굵게 등)은 표준 마크다운을 가정할 뿐 GitBook 특유의 요구사항을
  검증하지 않았다.
- **실제 깃북 게시** — GitHub PR도, 깃북 API 호출도 하지 않는다. 사람이 초안을 검토하고
  직접 깃북 에디터에 붙여넣는다(D4 원칙).
- **시트 diff·PR 이력 자동 수집** — 설계 문서는 이 스킬의 입력을 "시트 diff + 기획서 + PR
  이력"으로 그렸지만, 이번 착수는 그 입력을 사람이 준비해서 `--input`으로 넘기는 것까지만
  가정한다. `datasheet-validate --baseline-csv`의 diff 출력을 사람이 요약해서 섹션으로
  옮기는 식으로 연계할 수는 있지만, 자동 연결은 만들지 않았다.

## 5. 근거

- `docs/9c-update-automation-self-check.md` ⑥ — 깃북 페이지에 내장된 `gitSync` 메타데이터
  (`direction: export`)로 GitHub 토큰이 불필요함을 확인한 조사 기록.
- `.claude/skills/release-guard/SKILL.md` / `tools/9c/lib/release-guard.ts`의
  `parseGitbookHead` — 버전 헤딩 렌더링 패턴(`<h2 id="id-{APV}">{APV}</h2>`)의 실측 근거,
  이 스킬이 그대로 재사용.
- 2026-09-01 깃북 릴리즈 노트 페이지 헤딩 직접 확인 — 200330~200470(15개)이 예외 없이
  +10 간격, 200480은 아직 없음(0건). 그중 200400~200470(8개)은 날짜도 확인됨(설계 문서
  부록 C, 2026-01-27~08-25) — +10 관행의 근거.
