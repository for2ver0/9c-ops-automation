# 아레나 시즌 준비 오케스트레이션

> 이 스킬은 2026-08-30 세션에서, 5개 스킬(1-5순위)이 전부 착수된 뒤 마지막으로 작성됐다. 새로
> 계산하는 게 하나도 없는 **가이드 전용** 스킬 — 실제 로직은 전부 하위 5개 스킬에 있다.

## 이 문서는 누구를 위한 것인가 — 반드시 먼저 읽을 것

**이 문서의 `bash` 코드블록은 에이전트(Claude)가 대신 실행하는 것이지, 사용자가 터미널에 직접
치는 게 아니다.** 사용자는 아레나 시즌 담당자이지 개발자가 아니다 — "이번 시즌 상금 표 만들어줘,
풀은 40만이야" 같은 자연어 요청만 하면 되고, 명령어·플래그·JSON을 볼 필요가 없다.

에이전트가 이 스킬을 따를 때 지켜야 할 것:

1. **사용자에게 명령어를 보여주지 않는다.** "이 명령을 실행하세요"라고 안내하지 말고, 에이전트가
   직접 Bash로 실행한다.
2. **원시 출력(JSON, 터미널 로그)을 그대로 붙여넣지 않는다.** 결과를 사람이 읽는 말로 요약한다 —
   "불변식 4개 다 정상입니다", "여기 하나 문제가 있어요: Heimdall 시즌 번호가 0으로 등록돼 있어서
   공지를 못 냅니다" 같은 식.
3. **사용자에게 묻는 건 오직 사람만 알 수 있는 결정뿐이다** — 아래 "사용자에게 물어야 하는 것"
   목록 참고. 시즌 목록·정책 ID·블록 번호처럼 라이브 API로 알아낼 수 있는 건 에이전트가 직접
   조회한다(예: `arena-announce --list`로 등록된 시즌 후보를 먼저 훑어본 뒤 사용자에게 확인).
4. **FATAL이 뜨면 다음 단계로 절대 진행하지 않는다.** 왜 막혔는지, 무엇을 어디서 고쳐야 하는지
   (백오피스 화면 이름까지) 평이한 말로 설명하고 멈춘다.
5. **실제 등록·게시·서명 버튼은 에이전트가 절대 안 누른다** — 아래 "핵심 제약" 참고. 그 대목에
   도달하면 "이제 여기서 실제로 [등록/게시/서명]해주세요"라고 명확히 요청하고 기다린다.

### 사용자에게 물어야 하는 것 (이것만 묻는다)

| 시점 | 물어볼 것 |
| --- | --- |
| 상금 표 생성 전 | `RankingPool`, 그룹별 배분 비율(기본값 7,8,7,9,12,18,18,12,6,3 제안 가능), 스테이킹 lv2/lv3·용기패스 배수 3종 |
| 시즌 프리뷰 전 | 어느 네트워크·어느 시즌(`arena-announce --list`로 후보를 먼저 보여주고 고르게 하는 게 좋다), 라운드 수, 필요 메달 수, Total Prize, 정책 ID 2개 |
| 등록 후 | "실제로 ManageSeasons에 등록하셨나요?" (등록 전엔 공지 단계로 못 넘어감) |
| 공지 전 | (필요시) 메달 조정 문단을 넣을지·어떻게 쓸지 |
| 정산 후 | 서명·전송해서 받은 txId |

**나머지는 전부 에이전트가 라이브 API·정책 지문·과거 데이터로 알아서 채운다.** 사용자가 숫자를
모르면 "잘 모르겠다"고 답해도 되고, 에이전트가 직전 시즌 값이나 관측 기준값을 제안한다.

## 핵심 제약 (다른 무엇보다 우선)

**모든 단계의 최종 확인·승인·실행은 사람이다.** `docs/arena-season-prep-spec.md` §1의 원칙이고,
5개 스킬 전부 이 위에서 만들어졌다.

- 실제 ManageSeasons 등록 클릭
- 디스코드 게시
- NCG 지급 서명(Sign)·전송(Stage)

**이 세 가지는 에이전트도, 5개 스킬도 절대 대신 하지 않는다.** 자동화가 하는 건 계산·대사·검증·
초안 생성까지다.

**단**, ManageSeasons 등록과 NCG 정산 실행 두 가지를 에이전트가 수행하도록 범위를 넓히는 방안이
`docs/arena-settlement-automation-design.md`에서 담당자 승인 하에 논의 중이다(서명·전송 직전 사람
확인은 계속 필수). 아직 구현되지 않았고 §4의 안전장치 미해결 항목이 남아 있어, 구현되기 전까지는
위 세 가지 전부 사람이 직접 한다는 원칙이 그대로 적용된다.

## 전체 흐름과 스킬 매핑

| 단계 | 누가 | 스킬 | 산출물 |
| --- | --- | --- | --- |
| 1. 상금 내용 결정 | **사람**(에이전트가 물어봄) | (없음) | `RankingPool`·배분 비율·배수 3종 |
| 2. 상금 표 생성 | 에이전트 실행 + 사람 검수 | `arena-reward-table --table-only` | PNG + 불변식 리포트 |
| 3. 시즌 데이터 프리뷰·등록 | 에이전트 실행 + **사람이 직접 등록** | `arena-season-preview` → **ManageSeasons 수동 입력** | 대사 리포트 → 실제 등록 |
| 4. 디스코드 공지 초안 | 에이전트 실행 + **사람이 직접 게시** | `arena-announce` | 초안 텍스트 |
| 5-6. 시즌 시작·진행·종료 | **사람이 지켜봄**, 에이전트는 점검만 | `arena-season-checklist --check-cache` | 캐시 상태 리포트 |
| 7. 정산(tx 확인) | 에이전트 실행(제한적) + **사람이 직접 서명·전송** | `arena-reward-table`(라이브) + `arena-settlement-check` | 위험 항목 리포트 + tx 상태 |
| (수시) 전체 상태 확인 | 에이전트 실행 | `arena-season-checklist` | 위 산출물 집계 |

⚠️ **스펙 문서 §3의 프로세스 순서와 실제 실행 순서가 다르다.** §3은 `상금 표 생성 → 디스코드 공지
→ 시즌 데이터 세팅` 순으로 적혀 있지만, `arena-announce`가 라이브 `/seasons`에서 시즌을 조회해야
동작하므로(등록 안 된 시즌은 조회가 안 됨) **실제로는 시즌 등록(3단계)이 공지(4단계)보다 먼저
와야 한다.** 담당자 확인 전까지는 이 표(기술적 의존성 순서)를 따른다.

## 단계별로 에이전트가 하는 일

### 1-2. 상금 표 생성

사용자에게 `RankingPool`·배분 비율·배수 3종을 자연어로 물어본다(기본 배분 비율은 제안 가능).
받으면 에이전트가 직접 실행:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/arena-reward-table.ts" --table-only --png <경로> --json --pool <값> --percentages <값> --players <값> --staking-lv2 <값> --staking-lv3 <값> --courage-pass <값>
```

결과 PNG를 사용자에게 보여주고(파일 경로 안내), 불변식 결과를 요약해서 전달한다. FATAL이 있으면
값을 다시 물어보고 재실행. 여기서 확정된 `RankingPool`은 3단계에서 다시 쓰이므로 기억해둔다.

**사람 확인 지점**: PNG·표 내용이 맞는지 확인받는다.

### 3. 시즌 데이터 프리뷰 → 등록

네트워크·시즌 정보를 모르면 `arena-announce.ts --list`(또는 `arena-season-preview`가 참조하는
라이브 `/seasons`)로 후보를 먼저 조회해 보여주고 고르게 한다. 확정되면:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/arena-season-preview.ts" --network <n> --season-group-id <값> --arena-type <값> --season-start-block <값> --round-interval 10800 --round-count <값> --required-medal-count <값> --total-prize <2단계 RankingPool과 동일값> --battle-policy-id <값> --refresh-policy-id <값> --reward-table-pool <같은 값>
```

대사 결과를 사람이 읽는 말로 요약(예: "직전 시즌과 잘 이어지고, 정책 ID도 정상 범위입니다").
FATAL이면(`seasonGroupId==0` 등) 무엇을 어디서 고쳐야 하는지(백오피스 화면·필드명까지) 구체적으로
설명하고 **여기서 멈춘다.**

**사람 확인 + 실제 행동 지점**: 문제없으면 "이제 이 9개 값을 ManageSeasons에 등록해주세요"라고
요청하고, 사용자가 등록을 완료했다고 확인해줄 때까지 다음 단계로 넘어가지 않는다.

### 4. 디스코드 공지 초안

**등록이 실제로 반영된 뒤에만** 실행 가능(사람이 "등록했다"고 확인해준 뒤):

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/arena-announce.ts" --odin-season-group-id <값> --odin-arena-type <값> --heimdall-season-group-id <값> --heimdall-arena-type <값>
```

FATAL이면(실제로 겪은 사례: `seasonGroupId=0`) 초안 자체를 안 보여주고, 등록 데이터를 백오피스에서
고쳐야 한다고 설명한다. 정상이면 **초안 텍스트를 사용자에게 그대로 보여주고**, 메달 문단이 필요할
수 있다는 WARN이 있으면 참고 문구를 보여주되 "그대로 쓰지 말고 다듬어야 한다"고 알려준다.

**사람 확인 + 실제 행동 지점**: "문구 괜찮으면 디스코드에 직접 올려주세요" — 게시는 에이전트가
절대 하지 않는다.

### 5-6. 시즌 진행 중 — 점검만

사용자가 "지금 상태 어때?"라고 물으면:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/arena-season-checklist.ts" --check-cache "odin,heimdall"
```

캐시가 죽었으면(FATAL, 503) 즉시 알린다. 뒤처짐(WARN)은 **이 환경에서 상시로 관측되는 상태**라고
설명하고 크게 걱정할 필요 없다고 안내한다.

### 7. 시즌 종료 후 — 실지급 계산 + tx 확인

시즌이 끝났으면 라이브 모드로 최종 표를 재생성:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/arena-reward-table.ts" --network <n> --season-type <값> --season-group-id <값> --pool <값> --percentages <값> --players <값> --staking-lv2 <값> --staking-lv3 <값> --courage-pass <값> --courage-pass-csv <용기패스 CSV 경로> --png <경로> --json
```

`skipped-ranks`/`staking-match-failures`/`courage-pass-premium-100` WARN이 있으면 반드시
강조해서 알린다(실지급 사고로 이어질 수 있음). 문제없으면 지급 리스트를 사람이 확정하게 한다.

**사람 확인 + 실제 행동 지점**: "확인되면 직접 NCG 서명·전송해주세요. 완료되면 txId를 알려주시면
성공 여부를 확인해드릴게요."

txId를 받으면:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/arena-settlement-check.ts" --network <n> --tx <txId> --log-file <경로>
```

⚠️ 유저별 실지급이 계산과 정확히 일치하는지는 아직 대조 못 한다(대조할 정본 데이터가 시스템에
없다는 게 확인됨) — tx가 실제로 성공했는지까지만 확인 가능하다고 정직하게 안내한다.

### (수시) 전체 상태 집계

각 단계 결과를 모아서 한 화면에 보고 싶다고 하면 `arena-season-checklist`로 4개 산출물 +
캐시 상태를 집계해서 요약 보고한다.

## 대화 예시 (에이전트가 이렇게 응답해야 한다)

> **사용자**: "이번 시즌 상금 표 좀 만들어줘. 풀은 40만이고 나머지는 지난 시즌이랑 똑같이 해줘."
>
> **에이전트**: (지난 시즌 값을 알아야 하면 라이브로 조회하거나 사용자에게 확인) → 도구 실행 →
> "상금 표 만들었습니다. 인원·비율 불변식 다 정상이고, PNG는 `reward.png`에 저장했어요. 1-2등
> 그룹은 기본 4,666 NCG, 풀 조건(스테이킹 lv3+용기패스)이면 14,000 NCG까지 받습니다. 이대로
> 진행할까요?"

이렇게, **명령어나 JSON이 아니라 결과와 다음 행동**을 보여주는 게 이 스킬의 목표다.

## 사람이 반드시 멈춰야 하는 지점 (요약)

1. 상금 표 검수 (2단계 후)
2. 시즌 데이터 대사 확인 **+ 실제 ManageSeasons 등록** (3단계)
3. 공지 문구 다듬기 **+ 실제 디스코드 게시** (4단계)
4. 정산 지급 리스트 확정 **+ 실제 NCG 서명·전송** (7단계)

이 네 곳 중 하나라도 자동으로 건너뛰면 스펙 문서의 핵심 제약을 어기는 것이다.
