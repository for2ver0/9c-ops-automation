# 정규 운영 업데이트 오케스트레이션

> 이 스킬은 2026-09-03 세션에서, 담당자가 설명한 7단계 운영 흐름을 그대로 옮겨 만들었다.
> `arena-season-prep`과 같은 **가이드 전용** 스킬 — 계산 로직은 전부 하위 스킬에 있다.
> 전체 현황 표는 `README.md` §2.0 참고.

## 이 문서는 누구를 위한 것인가 — 반드시 먼저 읽을 것

**이 문서의 `bash` 코드블록은 에이전트(Claude)가 대신 실행하는 것이지, 사용자가 터미널에 직접
치는 게 아니다.** 사용자는 업데이트 운영 담당자이지 개발자가 아니다 — "이번 이벤트 던전 기획서
여기 있어, 시트 확인해줘" 같은 자연어 요청만 하면 되고 명령어·플래그·JSON을 볼 필요가 없다.

1. **명령어를 사용자에게 보여주지 않는다.** 에이전트가 직접 Bash로 실행한다.
2. **원시 JSON·터미널 로그를 그대로 붙여넣지 않는다.** 사람이 읽는 말로 요약한다.
3. **사람만 결정할 수 있는 것만 묻는다** (아래 표).
4. **FATAL이 뜨면 다음 단계로 절대 진행하지 않는다.** 무엇이 왜 막혔는지, 어느 시트의 어느
   행을 고쳐야 하는지까지 구체적으로 말하고 멈춘다.
5. **업로드·게시·배포 버튼은 절대 대신 누르지 않는다** (아래 "핵심 제약").

### 사용자에게 물어야 하는 것 (이것만 묻는다)

| 시점 | 물어볼 것 |
| --- | --- |
| ① 시작 시 | 기획서 파일 경로(또는 본문 붙여넣기), 이번 업데이트 타겟(어드벤처/아레나/이벤트 던전/인피니트 타워 등) |
| ② 검증 전 | 이번에 건드린 시트(탭) 목록과 CSV export 경로/URL, 각 시트의 키 컬럼(보통 `Id`), 직전 회차 CSV가 있으면 그 경로 |
| ② 대사 중 | 기획서에 수치가 명시 안 된 항목("밸런스 소폭 조정" 같은 문장)은 어떤 값이 맞는지 |
| ③ 게이트 통과 후 | "실제로 백오피스 스테이징에 올리셨나요?" (올라가야 QA 단계로 넘어감) |
| ④ QA 후 | QA 피드백 내용, 반영이 끝났는지 |
| ⑤ 릴리즈 노트 전 | 이번 버전(APV), 카테고리별 변경 항목 문구 |
| ⑥ 공지 전 | 인게임 공지가 이미 라이브에 올라갔는지(안 올라갔으면 announce-fanout이 읽을 원문이 없음) |
| ⑦ 배포 전후 | "Manage Apv 워크플로 실행하셨나요?" |

나머지(시트 구조, 행 수 변화, APV 결번, 공지판 일관성 등)는 전부 에이전트가 도구로 직접 확인한다.

## 핵심 제약 (다른 무엇보다 우선)

**D4 원칙 — 자동화는 라이브를 바꾸는 호출을 하지 않는다.** 아래 넷은 에이전트도, 하위 스킬도
절대 대신 하지 않는다:

1. 백오피스 스테이징/메인넷 **데이터시트 업로드(`/table-patch`)·Sign**
2. **깃북 릴리즈 노트 게시**
3. **디스코드 공지 게시** (자동 게시 경로 자체가 없다 — 웹훅·봇 없음, 항상 사람이 수동)
4. **메인넷 배포 실행**(9c-infra "Manage Apv" 워크플로 트리거)

자동화가 하는 건 계산·대사·검증·초안 생성·체크리스트까지다.

## 전체 흐름과 스킬 매핑

| 단계 | 누가 | 스킬 | 산출물 |
| --- | --- | --- | --- |
| ① 기획서 전달 | **사람** | (없음) | 기획서 파일/텍스트 |
| ② 데이터시트 작성 + 재확인 | 에이전트 지시서·검증 + **사람이 승인**(입력은 사람이 직접 하거나, 승인 시 에이전트가 `--apply`로 대행 — 아래 §2 참고) | `spec-to-datasheet` [→ `spec-to-datasheet-apply`] → `spec-datasheet-check` + `datasheet-validate` | 작업 지시서, 계획/assertions JSON, 검증 리포트[, 감사 로그] |
| ③ 인터널(백오피스 스테이징) 배포 | 에이전트 게이트 + **사람이 직접 업로드** | `datasheet-release-gate` | 시트별 게이트 리포트 |
| ④ QA 리뷰 | **사람(QA 담당자)**, 에이전트는 체크리스트만 | `qa-checklist` | 전/후 diff 체크리스트 |
| ⑤ 피드백 반영 → 깃북 릴리즈 노트 | 에이전트 초안 + **사람이 게시** | (③④ 반복) → `release-notes` | 릴리즈 노트 초안 |
| ⑥ 디스코드 공지 | 에이전트 초안 + **사람이 게시** | `announce-fanout` | 공지 초안 |
| ⑦ 메인넷 배포 | 에이전트 체크리스트 + **사람이 실행** | `deploy-prep` + `release-guard` | 배포 전/후 체크리스트 |

⚠️ **⑥의 순서 제약**: `announce-fanout`은 **이미 게시된** 인게임 공지판(`TextNotice{,_KR,_JP}.json`,
공개 CDN)을 읽어 디스코드용으로 재포장한다. 즉 인게임 공지가 라이브에 올라가기 전에는 이 스킬로
초안을 만들 수 없다 — 원문 자체가 없기 때문이다. 담당 팀이 확인해준 월간 릴리즈 순서도
`APV 범프 → latest.json → 인게임 노트·팝업·깃북 → 디스코드`로, 공지가 배포 **뒤**에 온다
(`docs/9c-update-automation-permission-request.md` ⑤). **담당자가 설명한 ⑤→⑥→⑦ 순서와 이 부분이
다르게 읽히는데, 담당자의 ⑦은 "데이터시트의 메인넷 반영"이고 릴리즈 순서 문서의 "배포"는
"클라이언트 APV 릴리즈"라 서로 다른 대상일 수 있다 — 아직 확인 안 됐다.** 순서가 애매하면 임의로
정하지 말고 담당자에게 "인게임 공지가 이미 올라갔나요?"를 물어서 판단한다.

## 단계별로 에이전트가 하는 일

### ① 기획서 받기

기획서는 **노션이 아니라 사람이 파일/텍스트로 직접 준다**(2026-09-03 확인). 노션 연동
(`spec-to-datasheet`)은 여전히 페이지 공유가 안 돼 착수 못 한 상태다 —
`docs/9c-update-automation-self-check.md` ② 참고. 기획서를 받으면 먼저 **읽고, 수치가 명시된
변경 항목을 전부 목록화**한다.

### ② 데이터시트 작성 + 재확인 (에이전트의 핵심 구간)

에이전트는 (a)~(e) 5단계로 진행한다 — **지시서 생성 → 시트 입력(승인 필요) → 기획서 대사 →
구조 검증 → 이상 보고**. (c)·(d)에서 문제가 나오면 원인에 따라 (a) 또는 (b)로 되돌아가
반복한다(자세한 분기는 아래 (e) 참고) — 한 번에 깨끗이 통과하리라고 가정하지 않는다.

**(a) 입력 작업 지시서** — 기획서에서 뽑은 계획 JSON을 현재 시트와 대조해 "무엇을 어떻게
바꿔야 하는지"를 먼저 뽑는다:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/spec-to-datasheet.ts" --csv <시트.csv> --plan <plan.json> --sheet-name <시트명> --key-column Id
```

변경(CHANGE)·새 행 추가(NEW_ROW)·이미 반영됨(NO_CHANGE)으로 분류해주고, 새 행에 값이 안 정해진
컬럼을 WARN으로 짚어준다. 컬럼명이 시트에 없으면(FATAL) 계획의 오타이거나 대상 시트를 잘못
고른 것이니 **여기서 멈추고 확인**한다.

**(b) 시트 입력** — (a)의 지시서를 사용자에게 보여주고 **대화형으로 명시적 승인**을 받는다.
승인 없이는 다음 단계로 넘어가지 않는다. 승인이 나면:

- 기본은 사람이 직접 구글 시트에 입력한다(D4).
- 2026-09-04부터 예외가 있다 — 사용자가 대행을 원하면 에이전트가
  `spec-to-datasheet-apply --apply`로 대신 쓸 수 있다(이중 게이트: 대화형 승인 + `--apply`,
  자세한 안전장치는 `docs/sheet-write-automation-design.md`). **이 경우에도 재계산에서 나온
  WARN·FATAL 항목은 절대 자동으로 쓰지 않는다** — 사람에게 그대로 보여주고 원본을 직접 고치게
  한다. 사람이 승인 없이 "그냥 알아서 넣어줘"라고 하더라도, (a)의 지시서를 먼저 보여주고
  명시적 확인을 받기 전에는 `--apply`를 실행하지 않는다.

**(c) 기획서 대사** — 입력이 끝나면 **같은 계획 파일을 그대로** assertions로 넘겨 검증한다
(형식이 동일해 변환 단계가 없다):

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/spec-datasheet-check.ts" --csv <시트.csv> --assertions <assertions.json> --sheet-name <시트명> --key-column Id --json > <시트>.speccheck.json
```

계획/assertions는 에이전트가 기획서를 읽고 만든다(`{sheet, id, column, expected, note}` — (a)에
쓴 `plan.json`을 그대로 넘기면 된다). **수치가 명시된 문장만 항목으로 만든다** — "밸런스를 소폭
조정" 같은 모호한 문장은 지어내지 말고 사용자에게 "이 항목은 구체적 수치가 없어 자동 대사가 안
됩니다"라고 알린다. 임의의 숫자를 넣으면 그 값이 시트에 입력되고 검증까지 같은 파일로 하므로
**틀린 값이 "일치"로 통과해버린다.**

**(d) 구조·이상 데이터 검증** — 시트(탭)마다 따로 실행:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/datasheet-validate.ts" --csv <시트.csv> --key-column Id --baseline-csv <직전회차.csv> --sheet-name <시트명> --json > <시트>.structural.json
```

중복 헤더·행별 컬럼 수 불일치·키 컬럼 공백·행 수 급감을 FATAL로 잡는다(v200450에서 실제로 터진
실패 모드 3종 포함). 회차 간 diff는 정보성이라 임계값 게이트가 없다 — **얼마나 바뀌었는지는 사람이
보고 판단**하게 요약해서 보여준다. (c)와 (d)는 서로 순서 의존성이 없다 — 둘 다 (b) 이후에만
돌리면 된다.

**(e) 이상 보고 → 사람 판단** — 담당자 요구사항 그대로 — **데이터가 이상하면 반드시 사용자에게
알린다.** FATAL이든, diff가 의도보다 커 보이든, 기획서에 수치가 없어 대사를 못 한 항목이든 전부
보고한다. 되돌아갈 지점은 원인에 따라 다르다:

- **계획(plan.json)은 맞는데 시트 입력이 틀렸거나 빠짐**(대부분 이 경우) — **(b)로** 돌아가
  다시 입력한다. 계획을 새로 뽑을 필요는 없다.
- **계획 자체가 기획서를 잘못 읽어서 틀림**(기대값이 기획서와 다름 등) — **(a)로** 돌아가
  계획부터 다시 잡는다.

어느 쪽이든 (c)·(d)를 다시 돌려 확인한다. 문제가 없으면 ③(인터널 배포 게이트)로 넘어간다.

### ③ 인터널(백오피스 스테이징) 배포

②의 두 산출물을 시트별 manifest로 묶어 게이트를 돌린다:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/datasheet-release-gate.ts" --manifest <manifest.json>
```

manifest는 `[{ sheet, structuralJson, specCheckJson }]` 배열이다.

⚠️ **이 게이트의 함정**: 어느 시트의 입력을 안 주면 그 시트는 체크 목록이 비어서 `level`이 그냥
`"OK"`로 계산된다("확인 안 함"이 "확인했는데 통과"처럼 보임). 출력의
`missingStructural`/`missingSpecCheck` 플래그와 `[WARN] 미실행` 표시를 **반드시 같이 읽고 사용자에게
전달한다** — "전체 OK"라고만 요약하면 안 된다.

**사람 확인 + 실제 행동 지점**: 전부 OK면 "이제 백오피스 스테이징에 이 CSV들을 올려주세요"라고
요청하고, 올렸다는 확인을 받을 때까지 ④로 넘어가지 않는다. **업로드는 에이전트가 하지 않는다.**

### ④ QA 리뷰

QA 담당자가 인터널에서 직접 확인한다. 에이전트는 "무엇이 바뀌었는지" 체크리스트만 만들어준다:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/qa-checklist.ts" --before <직전회차.csv> --after <이번회차.csv> --key-column Id --sheet-name <시트명>
```

⚠️ 이 스킬은 **"그래서 무엇을 테스트해야 하는지"는 알려주지 못한다**(시트별 기능 매핑은 lib9c 도메인
지식이 필요해 미착수). 추가·삭제·변경된 행 목록까지가 전부라고 정직하게 안내한다.

### ⑤ 피드백 반영 반복 → 깃북 릴리즈 노트

QA 피드백이 오면 시트를 고치고 **②→③→④를 다시 돈다**(피드백 없을 때까지 반복). 반복이 끝나면
릴리즈 노트 초안:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/release-notes.ts" --apv <버전> --input <sections.json>
```

`--input`은 사람이 준 카테고리별 항목이다 — **이 스킬은 문구를 새로 짓지 않는다.** 이미 게시된
버전 재사용, +10 관행 이탈, 빈 섹션 같은 대사만 해준다.

**사람 확인 + 실제 행동 지점**: "초안 확인하시고 깃북 에디터에 직접 붙여넣어 게시해주세요."
깃북은 에디터 직접 입력 방식이고 GitHub 레포는 편도 백업(export)이라, **GitHub PR로 반영하려
시도하면 안 된다**(다음 export 때 덮어써짐 — `docs/9c-update-automation-self-check.md` ⑥).

### ⑥ 디스코드 공지 초안

**인게임 공지가 라이브에 올라간 뒤에만** 가능하다(위 순서 제약 참고):

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/announce-fanout.ts"
```

언어별(EN/KR/JP) 버전 불일치·빈 본문·번역 누락 의심을 같이 잡아준다. 초안은 **검증된 고정
템플릿이 아니라** 인게임 공지를 재포장한 것이므로, 채널의 과거 게시물과 비교해 다듬어야 한다고
반드시 같이 알린다(정규 업데이트 디스코드 공지의 실제 과거 샘플을 아직 확보 못 함).

**사람 확인 + 실제 행동 지점**: "문구 다듬어서 announcement 채널에 직접 올려주세요."

### ⑦ 메인넷 배포

배포 전 체크리스트·롤백 스냅샷·Manage Apv 입력값:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/deploy-prep.ts" --snapshot-log <로그.jsonl>
```

배포 전후로 깃북·매니페스트 APV·인게임 공지판·LiveAssets 네 곳의 일관성 대조:

```bash
bun run "$(git rev-parse --show-toplevel)/tools/9c/release-guard.ts" --log-file <로그.jsonl> --event-log-file <event로그.jsonl>
```

`release-guard`는 실행할 때마다 결과가 바뀌는 진단 도구다 — 과거 실행 결과를 현재 상태로 인용하지
않는다.

**사람 확인 + 실제 행동 지점**: "계산된 입력값으로 9c-infra의 Manage Apv 워크플로를 직접
실행해주세요." 실행 후 `release-guard`를 다시 돌려 네 곳이 맞는지 확인해준다.
